# Canon translations

Status: **normative**, for language version 0.1. Companion to [SPEC.md](../SPEC.md) §17 and
[VIEWMODEL.md](VIEWMODEL.md). This document fixes which texts are translatable and under which
key, what a translation file may contain, how missing translations are reported and displayed,
and the exact behaviour of `canon i18n stub` and `canon i18n status` (CLI.md §3.11).

Settled here: AUDIT I18N-01…04, CHK-03, GEN-07 (the `W1701` part), and MOCKUP-GAPS 12, 39, 45 and
46 (DECISIONS 9, 20).

"MUST", "MUST NOT", "SHOULD" and "MAY" are used in their RFC 2119 sense. Every numbered rule
(`K3`, `F2`, …) is a test target.

## 1. Texts and languages

- **L1.** The **source language** is the first entry of `project.languages`. Every text is written
  in it, in the sources: doc comments, view labels and texts, `@deprecated` reasons, check
  messages, `@menu` labels. Other languages live in translation files (§4).
- **L2.** These are **tool texts**: what the studio and the compiler show to developers and
  designers. Game texts (item names, quests) are data and stay in the game's text tables
  (SPEC §17).
- **L3.** **Studio chrome** is owned and translated by the studio itself, never by Canon: "More",
  "Other" (the `_other` group), "Unused fields", "No menu", "Add", "Any", "(none)", "none", "Unset",
  "Yes", "No", "Clear", "Reset to default", "min", "max", "#1", "retired", "Rename…", "Undo", and
  the fallback marker and banner (§6).
- **L4.** Compiler diagnostics (the message templates of the diagnostic registry) are not
  translated in this version. Only the messages of named checks are (§3.3).

## 2. Which texts are keys

- **L5.** A text is **plain** or a **template**. Templates are: `title`, `subtitle`, the second
  string of `show`, `step`, and check messages. Every other text is plain (VIEWMODEL.md G14).
- **L6.** A text is **translatable**, and gets a key, when it contains at least one Unicode letter
  (general category `L`) outside its interpolations (after unescaping). `"{id}"`, `"{count} × {item}"`
  and `" %"` are not translatable: they read the same in every language. `"Level {level}"` and
  `" HP"` are. This refines I18N-01 ("texts with no literal characters are not keys").
- **L7.** A text that is not translatable is written in the view model as a language-neutral text
  (`{"text": "…"}`, VIEWMODEL.md J9) and never counts as missing.
- **L8.** Labels always exist: a field, method, value, enum member or variant case without a
  written label gets a default (VIEWMODEL.md X1: humanized name, or Canon name). The default is the
  key's source text and is translatable like any other (MOCKUP-GAPS 39).

## 3. The key catalogue

The **catalogue** of a package is the set of its keys, each with its source text. It is computed
by the compiler; translation files are checked against it and the view model's `i18n` holds it.

### 3.1 Which declarations contribute

- **K1.** The catalogue covers the declarations the package's view model describes (VIEWMODEL.md
  §12.1): every type in its `types` (the package's public types and every type of the package
  reachable from a public type or value, `local` ones included), every public top-level `let`,
  every define-table view, every named check of those types and of the package.
- **K2.** Methods contribute only when a view names them. Export functions, widgets, constants,
  tests and the package doc comment contribute nothing (widget docs are developer texts).
- **K3.** The package named by `project.studio` is a vocabulary: its catalogue holds only
  `Menu.<member>` (and `Menu.<member>.help` when the member has help) and `units.<unit>.suffix`
  for each unit whose suffix is translatable (MOCKUP-GAPS 46). Its other declarations contribute
  nothing.

### 3.2 Key syntax

A key is a dot-separated sequence of identifiers (GRAMMAR.md `translationKey`); reserved words
are allowed as segments (LEX-08). Unnamed `show` lines use ids `_0`, `_1`, … (identifiers the
program cannot declare, VIEWMODEL.md G17).

The **reserved segments** are:

```
help title subtitle singular plural group show check intro text
deprecated placeholder none step field method case member
```

- **K4.** A field, method, variant case or enum member whose name is a reserved segment is written
  with its **kind word** in front: `field.<name>`, `method.<name>`, `case.<name>`,
  `member.<name>`. Any other name is written bare. Only that form is valid; the other is a key
  that matches nothing (`E1702`). Examples: the label of a field named `title` is
  `Quest.field.title`; the help of an enum member named `check` is `Icon.member.check.help`.
- **K5.** With K4, every key names exactly one text: reading a key left to right, a segment that is
  a kind word is followed by a name, another reserved segment is a text part, anything else is a
  name. The first segment of a key is always a name (a type, a top-level `let`, `check`,
  `Menu` or `units`); the reading applies from the second segment.

### 3.3 The keys

`T` is a record, variant or enum name; `f` a field; `m` a method; `c` a variant case; `e` an enum
member; `v` a top-level `let`; `g`, `s` group and show ids; `n` a check name. "Doc" is
the doc comment normalized by LEX-07. A key exists only when its text exists and is translatable
(L6), except labels (L8).

| Key | Exists for | Source text | Kind |
|---|---|---|---|
| `T.help` | a record, variant or enum with a doc comment | doc | plain |
| `T.f` | every field of a record | view label, else humanized name | plain |
| `T.f.help` | a field with a `help` property or a doc comment | `help`, else doc | plain |
| `T.f.deprecated` | a `@deprecated("…")` field | the reason | plain |
| `T.f.placeholder` | a `placeholder` property | it | plain |
| `T.f.none` | a `none` property (MOCKUP-GAPS 12) | it | plain |
| `T.f.step` | a `step` property | it | template (`{index}` only) |
| `T.m` | a method named by a view | view label, else humanized name | plain |
| `T.m.help` | such a method with `help` or a doc comment | `help`, else doc | plain |
| `T.title`, `T.subtitle` | the view item | it | template |
| `T.singular`, `T.plural` | the view item | it | plain |
| `T.group.g` | a group | its label | plain |
| `T.group.g.intro` | a group intro | it | plain |
| `T.show.s` | a `show` line (`s` its id, or `_<n>`: 0-based position among the view's unnamed `show` lines) | its label | plain |
| `T.show.s.text` | the same | its template | template |
| `T.check.n` | a named one-line `check` or `warn` of a record, or of a variant outside its cases | its message | template |
| `T.c` | every case of a variant | label from `view T`, else the Canon name | plain |
| `T.c.help` | a case with `help` in `view T`, or a doc comment | `help`, else doc | plain |
| `T.c.<part>` | the items of `view T.c` and the checks of the case: `title`, `subtitle`, `singular`, `plural`, `group.g…`, `show.s…`, `check.n` | as for records | as for records |
| `T.c.f`, `T.c.f.help`, … | every field of a case, with the field sub-keys above | as for records | plain |
| `T.e` | every member of an enum | label from the enum's view, else the Canon name | plain |
| `T.e.help` | a member with `help` in the view, or a doc comment | `help`, else doc | plain |
| `v` | a public top-level `let` | `@menu(label: …)`, else humanized name | plain |
| `v.help` | such a `let` with a doc comment | doc | plain |
| `v.title`, `v.subtitle`, `v.singular`, `v.plural` | a define-table view on `v` (`v` may be `local`) | it | as for records |
| `check.n` | a named one-line `check` or `warn` at package level (CHK-03) | its message | template |
| `Menu.e`, `Menu.e.help` | studio package only (K3) | as for enum members | plain |
| `units.u.suffix` | studio package only (K3) | the unit's `suffix` | plain |

- **K6.** Column headers and filter labels reuse the field's label key; there is no separate key
  (I18N-01).
- **K7.** A case field labelled in the view of the parent record that inlines the variant keeps
  its own key `T.c.f`; the parent view only supplies its source text (VIEWMODEL.md G10); a parent view in another package supplies
  nothing (a package's catalogue is built from that package alone, I18N-04).
- **K8.** Unnamed checks, block-form checks (`fail(x, "…")`, `warn(x, "…")`) and compiler
  diagnostics have no key: their messages are shown in the source language only. Naming a check
  makes it translatable.
- **K9.** Retired members, cases and deprecated fields keep their keys (they are still shown).
- **K10.** Catalogue order is the byte order of the keys. `canon i18n stub`, `canon i18n status
  --list` and the view model's `texts` use it.

## 4. Translation files

A translation file starts with `package <p>` then `translation <lang>`, and holds only entries
`<key> <string>` (SPEC §3.3, §17).

- **F1.** The file's `package` line follows the package rules of SPEC §3.2 (a file of the package's
  directory or of a subdirectory). Its keys are keys of that package's catalogue (I18N-04). By
  convention the file is `<dir>/<last segment>.<lang>.canon` (`resource/farm/farm.fr.canon`).
- **F2.** `<lang>` MUST be one of `project.languages` (`E1704`) and MUST NOT be the source language
  (`E1706`).
- **F3.** A package MAY have several files for one language; they are merged. A key given twice,
  in one file or in two, is `E1705` at the second occurrence (files in path order, then source
  order).
- **F4.** A key that is not in the catalogue is `E1702` at the key (SPEC §17): renaming a field
  makes its translations errors immediately. A key whose declaration or view is broken (left out of the catalogue,
  VIEWMODEL.md J4), or whose first segment names nothing while a source file of the package lost part of
  its syntax to an error (the parser recovered by dropping a declaration, statement, expression or
  type; a lexical error inside a construct that still parses does not count; a `check.<n>` key
  counts as naming nothing then), is not `E1702`: the broken declaration's own finding stands alone (TYPES.md §1). The message adds a hint when the key names a text
  that exists but is not translatable ("its source text has no letter"), or when only the K4 form
  differs ("write `Quest.field.title`").
- **F5.** The text is any string literal (plain, raw or multiline, GRAMMAR.md). An **empty** text
  (`""`) counts as missing (§5); it is how `canon i18n stub` leaves a key to fill.
- **F6.** A translation of a plain text MUST NOT contain an interpolation (`E1707`, at the first
  interpolation); a literal brace is written `{{` or `}}`. Source texts are held in this form
  too, whatever the source string's kind.
- **F7.** Translation files are checked by `canon check` and `canon build` like sources; their
  errors block a build (the view model is still written, VIEWMODEL.md J4).
- **F8.** Rewording a source text does not invalidate its translation: keys are paths, never texts.
  Stale translations are not detected in this version.

## 5. Missing translations: W1701

- **W1.** For each selected package **that has an `emit view`** and each language of
  `project.languages` other than the source, let `missing` be the number of catalogue keys without
  a non-empty translation. When `missing > 0` the compiler reports **one** `W1701` for that
  (package, language) (I18N-03), never one per key. A package without `emit view` gets no
  `W1701`; its translation files are still checked (F1–F7), and `canon i18n status` still counts
  its keys (§10).
- **W2.** Location: the `translation` line of the package's first translation file for that
  language (path order); without one, the `package` clause of the package's first source file
  (path order). The finding has no value path.
- **W3.** Message: the variants of `W1701` in [ERRORS.md](ERRORS.md) (`many` with `n` = `missing`,
  `one` when it is 1), which name the `canon i18n status … --list` command that lists the keys.
- **W4.** Humanized labels and Canon-name labels count (MOCKUP-GAPS 39). Non-translatable texts do
  not (L7).
- **W5.** `canon check --max-warnings 0` therefore fails while any translation is missing; a
  project that accepts gaps during migration sets a higher limit (CLI.md §6.2).

## 6. Fallbacks

- **B1.** Wherever a text is needed in language `L` and `L` has no non-empty translation for its
  key, the source text is used (SPEC §17). The view model gives the studio both tables
  (VIEWMODEL.md §12.10); `Evaluate` renders templates in `Lang` with this fallback and sets
  `Text.Fallback` (API.md V8).
- **B2.** Display (MOCKUP-GAPS 45): a text shown in the source language because its translation is
  missing carries a small marker with the source language's code in upper case ("EN"), in forms,
  headings, group titles, help texts and menus. Table cells and picker rows carry no marker. The
  marker applies to static texts and to rendered texts whose `Fallback` is true.
- **B3.** When a package has **no** translation file for `L` (`i18n.languages[L].files` is empty),
  the studio shows no per-text marker for that package's texts and one banner on each of its
  screens: "No <language> translation for <package>: texts are shown in <source language>"
  (studio chrome).
- **B4.** Developers MAY hide markers and banners (a studio preference).
- **B5.** `canon check --lang L` (and `Options.Lang`) writes the messages of named checks in `L`
  when translated, else in the source language. The view model holds every language: `message`
  in the source language and `messages` for the others (VIEWMODEL.md J15).

## 7. Templates

- **T1.** A translation of a template key MAY be a template (I18N-02), whether or not the source text
  has interpolations. It is checked in the **scope of the source item**: a view template in the
  scope of VIEWMODEL.md §3.4, a check message in the scope of its check, a `step` text with only
  `{index}`.
- **T2.** Each interpolation is type-checked with TYPES.md; any error is reported as `E1703` at the
  interpolation, with the type error as its detail.
- **T3.** A translation may use other interpolations than its source, in any order, and may omit
  some (`"Palier {level}"` for `"Level {level}"`). Format specs (`{x:,}`) are allowed.
- **T4.** Rendering follows VIEWMODEL.md §9.2 in the translation's language (enum members by their
  translated label, refs by their target's title).

## 8. Numbers and units

- **U1.** A unit's suffix is translated in the studio package's files under `units.<unit>.suffix`
  (MOCKUP-GAPS 46): `units.hp.suffix " PV"`. The leading space is part of the text.
- **U2.** Numbers in controls follow the language's conventions (VIEWMODEL.md X9): decimal mark and
  grouping separator, never the text of a translation. Numbers in rendered templates are not
  localized (VIEWMODEL.md X5).

## 9. `canon i18n stub`

```
canon i18n stub <lang> [packages…]
```

Adds every missing key of the selected packages to a translation file, so a translator only fills
in texts.

- **S1.** `<lang>` MUST be in `project.languages` and not the source language, else the command
  prints a usage error and exits 2.
- **S2.** For each selected package, the keys to add are the catalogue keys that appear in **no**
  translation file of `<lang>` (keys present with `""` are left alone). A package with none is
  untouched.
- **S3.** Target file: `<package dir>/<last segment>.<lang>.canon` if it exists; else the package's
  first translation file for `<lang>` in path order; else a new file
  `<package dir>/<last segment>.<lang>.canon` containing exactly `package <package>` LF
  `translation <lang>` LF.
- **S4.** Appended text: one empty line (unless the file already ends with an empty line or is new),
  then for each key in catalogue order (K10): the source text as comment lines (each line of the
  source text prefixed with `// `, or `//` for an empty line), then `<key> ""`. Multiline source
  texts give several comment lines; templates are shown as written, with their `{…}`.
- **S5.** Existing lines are never changed, reordered or removed; unknown keys stay (and remain
  `E1702`). The written file is a fixed point of `canon fmt`.
- **S6.** Standard output, one line per file written, in path order, then a summary:

```
pipeline/pipeline.fr.canon  +14 keys (new file)
resource/farm/farm.fr.canon  +15 keys
29 keys added to 2 files
```

  With nothing to add: `nothing to add`. Exit code 0; 2 for usage errors; 1 if a file cannot be
  written.
- **S7.** `canon i18n stub` does not run checks and writes nothing else. It does not need the
  project to be free of errors, but it needs the selected packages to type-check (the catalogue
  depends on the views); otherwise it prints the findings and exits 1.

## 10. `canon i18n status`

```
canon i18n status [packages…] [--lang <lang>]… [--list] [--format text|json]
```

- **R1.** For each selected package and each non-source language (or only the `--lang` ones), in
  (package, language) order, one row: `keys` (catalogue size), `translated` (non-empty
  translations of catalogue keys), `missing` (`keys - translated`), `unknown` (keys that are
  `E1702`), `files` (the package's translation files for that language).
- **R2.** Text output: a table with the header `package lang keys translated missing unknown
  files`. Columns are separated by two spaces; `package`, `lang` and `files` are left-aligned, the
  counts right-aligned; each column is as wide as its widest cell or header; no trailing spaces.
  `files` is a comma-separated list, or `-`. Then a summary line
  `{p} packages, {m} missing, {u} unknown`.

```
package        lang  keys  translated  missing  unknown  files
pipeline       fr      14           0       14        0  -
resource.farm  fr      61          46       15        0  resource/farm/farm.fr.canon
2 packages, 29 missing, 0 unknown
```

- **R3.** `--list` adds, after the table, one line per missing or unknown key, sorted by package,
  language, then `missing` before `unknown`, then key:
  `{package} {lang} missing {key}` and `{package} {lang} unknown {key} {file}:{line}:{col}`.
- **R4.** `--format json` prints one object per row, then a summary object, one per line:

```json
{"package":"pipeline","lang":"fr","keys":14,"translated":0,"missing":14,"unknown":0,"files":[]}
{"summary":{"packages":1,"missing":14,"unknown":0}}
```

  With `--list`, each row object also has `missingKeys` (strings, catalogue order) and
  `unknownKeys` (`{"key","file","line","col"}`), placed after `files`.
- **R5.** Exit code: 0; 1 when a selected package's translation files have an `E17xx` error;
  2 for usage errors.

## 11. Examples

The farm (`examples/resource/farm`): `farm.fr.canon` translates, among others:

```
FarmConfig.title "Ferme"
ModelType.group.unlock.intro "Ce que le joueur paie pour débloquer ce modèle."
Level.title "Palier {level}"
ModelType.check.unreachable_levels "maxLevel vaut {maxLevel} mais seuls {levels.len()} paliers existent"
Global.maxModels.deprecated "Jamais lu par LoadFromFile : …"
```

Every key is in the catalogue: `FarmConfig.title` ("Farm" has letters), `Level.title` (a template
with letters: its translation may interpolate `{level}`, T1), `ModelType.check.unreachable_levels`
(a named `warn`). `ItemCost.title` (`"{count} × {item}"`), `Bonus.title`
(`"{attribute} ({value})"`) and `ModelType.title` (`"{typeName}"`) have no letter and no key:
translating them would be `E1702`, so `farm.fr.canon` has no entry for them. `Bonus`'s `warn` is
unnamed, so it has no key either (K8).

With the examples as written, the farm's catalogue has 88 keys: 6 type docs (`T.help`), 27 field
labels and 27 field helps (every field has a doc comment), 1 deprecation reason, 1 placeholder, 3
titles (`FarmConfig`, `Global`, `Level`), 4 `singular`s, 11 group labels, 3 group intros, 3 named
checks, and the value's label and help (`farm`, `farm.help`). `farm.fr.canon` translates 49 of
them. The 39 missing ones include most field helps (`ModelType.typeName.help`, a doc comment),
`Level.level` (the humanized label "Level"), `Global.maxModels` and the value label `farm`, so
`canon check` reports one `W1701` for (`resource.farm`, `fr`): "39 texts of package
resource.farm have no fr translation (…)".

The pipeline (`examples/pipeline`) has 14 keys and no French file:

```
Potion.check.fast_big_heal   Potion.cooldown   Potion.cooldown.help   Potion.heal
Potion.heal.help   Potion.help   Potion.id   Potion.id.help   Potion.name   Potion.name.help
Potion.stack   Potion.stack.help   potions   potions.help
```

`canon i18n stub fr pipeline` creates `pipeline/pipeline.fr.canon`:

```
package pipeline
translation fr

// heals {heal} every {cooldown}: that outheals most bosses
Potion.check.fast_big_heal ""
// Cooldown
Potion.cooldown ""
// Time before the same potion can be drunk again.
Potion.cooldown.help ""
…
// One JSON file per potion, as today. Each file is one entry; findings point into it.
// Reloadable: tuned live during balance sessions, and runtimes keep potion ids, never
// Potion pointers, across ticks.
potions.help ""
```

## 12. Diagnostics

Codes `E17xx` / `W17xx`.

Messages (templates and typed arguments) are defined only in [ERRORS.md](ERRORS.md), the single
source of diagnostics (DECISIONS 27); this table says when each code fires.

| Code | Severity | Trigger |
|---|---|---|
| W1701 | warning | W1–W4 |
| E1702 | error | F4 |
| E1703 | error | T1, T2 |
| E1704 | error | F2 |
| E1705 | error | F3 |
| E1706 | error | F2 |
| E1707 | error | F6 |

The single catalogue of every code is [ERRORS.md](ERRORS.md).
