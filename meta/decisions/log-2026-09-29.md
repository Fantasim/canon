- **Journal threat model (U4c round 3; API §2 O5/§10.3 silent).** A journal may come from a hostile
  repository, and a hostile `project.canon` may declare roots anywhere (SPEC §4). Defences, all
  required: Recover/rollback never traverse a symlink (every component resolved must equal the
  lexical path; `removeAll` removes a link, never descends it); no `.`-prefixed path segment; file
  paths only with extensions the edit API writes (`.canon`, `.json`); modes only rw permission bits;
  a journal written on another host is kept and never applied automatically (Open fails naming
  it); the new-content digest gates every restore or removal, so an attacker cannot overwrite or
  delete an existing file without knowing its exact bytes; a created directory is cleared only when
  it holds nothing but the journal's own new files, their stages and temp leftovers (a user file
  added after a crash keeps the journal). Residuals, accepted and documented: a reused PID keeps a
  dead writer's journal "running"; the cross-process idle check is not atomic.
