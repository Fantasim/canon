## Performance: halve `check` and `build` memory and time (Louis, 2026-10-14)

- **Baseline on Resource** (456c1bcd, v0.1.7, 3 runs, load 2-6.5): `check` 17.5 s, 2.83 GB peak;
  `build --check` 21.3 s, 2.87 GB. Live heap ~1.5 GB (the rest is GOGC=100 headroom). The mutator
  runs on one thread; GC is ~half of CPU samples. Live heap: syntax 34%, eval 34-47%, check 10%.
  Profile and pprof files: the session scratchpad `perf-profile-2026-10-14.md` (not kept).
- **Token store → DECISIONS 371** (frozen contract §4.1, approved by Louis). Trivia is read back
  from the bytes; Token is 12 bytes. Resource peak RSS: `check` 2.66-2.85 → 2.20-2.31 GB,
  `build --check` 2.87-3.29 → 2.35-2.49 GB. Wall time not judged (load 7-17 during the A/B).
  Review: equivalence byte-identical over 604k parses; the test gap on GRM-08 closed by
  `TestTriviaKinds` (fails under both reviewer mutations).
- **GC knobs: rejected.** GOMEMLIMIT 1.5/2 GiB and GOGC=50 cut RSS 23-35% but trade CPU (the
  1.5 GiB limit thrashes); none halves memory since live data is ~1.5 GB. Defaults stay.
- **`std.findIndex` drives 55% of all allocation**, through ~20 M predicate calls: Resource's
  `tidCode` (`events/vocab/display/display.canon:100`, copies in `recordbook/boards.canon:120`,
  `ranking/names.canon:58`) scans the 9,455-member `TextId` by name per field per row. Cause is
  Resource's modelling (`type Tid = String(/^TID_…$/)` instead of a `TextId` reference) and
  Canon's: no cheap name-to-member path, no warning. Owed: a Resource handoff; on Canon's side
  cheaper lambda calls (running, EVAL) and an enum by-name lookup with a lint on the scan pattern
  (to decide after the lambda numbers).
- **Owed levers, ranked:** lambda calls copy their captures (~19% of allocation); `value.Prov`
  slimming/interning (26% of live heap); per-package parallelism of stages A, C/D, E (the only
  big wall-time lever; the evaluator's memo, depth and budget must split per package first).
- **Lambda captures landed (4cca5d42).** Closures share a read-only capture list; frames bind
  four names in place; an unnamed frame reuses its caller's stack. Review PASS after a test pinned
  the stack reuse (`TestLambdaValueStack`). Bench: 150,883 → 120,875 allocs/op; Resource wall not
  judged (load 21-36). Peak RSS unchanged, as expected.
- **Resource `tidCode` measured** on a patched copy (cached `toMap`): `check` wall −35%, user CPU
  −43%, RSS +5%, findings identical. Handoff `2026-10-14-canon-to-resource-tidcode.md`. Resource's
  `Tid = String` is a workaround: a `TextId` field would need an enum its consumers never get
  (F20). Canon's share: F20 and a by-name lookup, so the obvious code is the fast code.
