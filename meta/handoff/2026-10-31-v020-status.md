## The one call that is yours: Go exhaustiveness (ADR-0023 §4, Decision 9)

Go enums without `@codes`, variant kind enums and dependent branch enums become opaque structs
(`type Tone struct{ position uint8 }`, `var` members, `Position()`), copied from v0.1.9's ids. So no
integer converts to or from them, and `<`, arithmetic, `%d`, `database/sql` and `gob` no longer leak
declaration positions.

**The cost:** Sovereign's `exhaustive` linter only sees enums made of constants, so the fleet rule
"a new enum value must break the build" (`sovcommon/tools/sovaudit/rules.md:254-256`) goes blind on
these Canon enums in Go. Canon's own `match`, C++ `-Wswitch`, TS string-union narrowing and the
generated tables stay exhaustive. The reply gives Go consumers the way out: a `default:` that returns
an error, plus a test that ranges over `<E>Members()` through each switch.

**Default: accepted, built as written.** If you veto, write it here (or tell the session) before
EN-GO starts (wave C at the earliest). EN-GO then waits and I ask you for the alternative in a file.
Nothing else waits on this.
