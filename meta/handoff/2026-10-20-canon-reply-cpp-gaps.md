## 1. Replacing `define*.h`: `@cpp(defines:)` (CODEGEN.md §7.9)

Canon already writes a define header from an enum. Annotate the id enum:

```canon
enum ItemId @codes(UInt32) @cpp(defines: "II_") {
  retired II_DEFAULT = 10
  II_WEA_HAN_HAND = 11
  …
}
```

The C++ emit then also writes `<out>/vocab.defines.gen.h`:

```cpp
// GENERATED by canon from items/vocab/. DO NOT EDIT.
#pragma once
#define II_DEFAULT 10
#define II_WEA_HAN_HAND 11
```

- **Names.** A member whose name already starts with the prefix keeps its name; any other member
  gets prefix + name.
- **Values.** With `@codes`, each value is the member's code. Without `@codes`, it is the member's
  declaration index, so every enum that stands for a define header must have `@codes` (they all do
  today).
- **Order.** Members are written in declaration order. Retired members are included.
- **Mixing with legacy headers.** Every generated header and source that names one of these
  enumerators wraps it in `push_macro`/`#undef`/`pop_macro`. A TU may therefore include the
  legacy `defineitem.h` or `vocab.defines.gen.h` before or after `vocab.gen.h`.

**Checked on 0.1.9** (`g++ -std=c++17`), in a TU including `vocab.gen.h` with either the legacy
define header or `vocab.defines.gen.h`:

- `switch (id) { case II_WEA_HAN_HAND: … }` compiles;
- `#ifdef II_GOLD_SEED1` works, so the 11 `#if`/`#ifdef` sites need no rewrite;
- `ItemIdFromCode(c)` and `static_cast<uint32_t>(v) == II_WEA_HAN_HAND` both compile.

**The one rule.** A TU in which the macro is live cannot write `ItemId::II_WEA_HAN_HAND` by name.
The preprocessor expands the member name. Such a TU gets the typed value with
`ItemIdFromCode(II_WEA_HAN_HAND)` or `static_cast<ItemId>(II_WEA_HAN_HAND)`. Loaders receive
`ItemId` values from `T::Parse`, so they rarely need to spell a member.

The unscoped `inline constexpr` constants you asked for would hit the same rule, since a constant
cannot share a name with a live macro either. They would also break the `#ifdef` sites. Canon
does not add them, because there would then be two mechanisms for one job.

**Migration.** Diff each `*.defines.gen.h` against the `define*.h` your `emit text` renders today.
When they match, switch the includes. The text emit can then stop rendering the header.

## 3. Reserved member names: `@cpp(name:)` (CODEGEN.md §3.5)

`_OI_DEFAULT`, `_NONE`, `_FIRE` and the like are reserved identifiers in C++: a leading underscore
followed by an uppercase letter. Rename them in the C++ output only. The annotation goes after the
value:

```canon
enum ObjId @codes(UInt32) {
  _OI_DEFAULT = 10 @cpp(name: "OI_DEFAULT")
}
```

- **What stays the same:** the Canon name, the wire name (`"_OI_DEFAULT"`, so the data spelling is
  unchanged) and `canon.lock`. No `E6001` is raised.
- **What changes:** C++ writes `ObjId::OI_DEFAULT`. `ToName` and `ToWire` still return
  `"_OI_DEFAULT"`.

The same goes for `ElementDefine._NONE`, `_FIRE`, `_WATER`, `_ELECTRICITY`, `_WIND` and `_EARTH`.
Pick names that are not platform macros (see W8006).

**`world.clientworld` `IDS_DUOMINOUS__WLD_000000`** is a different case: it is a table key, not an
enum member, and only a `baked` emit turns keys into a C++ enum. A key takes no annotation.

A mangling rule is no answer either. Dropping the `__` would collide with the neighbouring key
`IDS_DUOMINOUS_WLD_000000`. Emit that package in `types` mode instead (or `data`), where table ids
are `std::string`.

## 5 (part). Root decoders for a file whose top level is a map or list

An exported `@text` fn whose result is a map, a list or a keyed list already gets a C++ decoder in
`types` mode (CODEGEN.md §5.13, DECISIONS 363). It is a function in the package namespace:

```cpp
std::optional<canon::FlatMap<std::string, TextEntry>>
DecodeMiniGameFindWordDescFileFile(std::string_view text, std::string& error);
```

- **Name.** `<Fn>` is the fn's name in UpperCamel. A fn named `…File` therefore gives `…FileFile`.
- **What it does.** It parses the text itself, keeping file order and applying the byte rules.
- **When it is missing.** On 0.1.9 the decoder is absent only when the result holds a map inside a
  record. v0.1.10 lifts that limit.
- **A file without a decoder.** If one of the ~15 TextEntry, TextRow or SkillText files has no
  exported `@text` fn rendering it, give it one.

## 6. Until v0.1.10: `INT32_MAX`, `UINT32_MAX`, `NAME_MAX`

Rename these constants for C++. On a `const`, the annotation goes on the line before it:

```canon
@cpp(name: "kInt32Max")
const INT32_MAX = 2147483647
```

Their Canon names do not change. On 0.1.9 an un-renamed `UINT32_MAX` breaks the generated header
silently. This was checked: no warning, and g++ fails.

## 7. One shared `canon_runtime*.h`: declined

Each `out` directory is self-contained by design, so copies can be moved and vendored on their
own. Every copy carries the same include guard (`CANON_RUNTIME_RT_V1`, `CANON_RUNTIME_JSON_RT_V1`).
Several copies on the include path, or included in one TU, are harmless: the first copy included
wins and the others compile to nothing.
